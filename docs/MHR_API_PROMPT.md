# დავალება: MHR-ში API HR დოკუმენტების გადამრჩევისთვის (HR Sorter)

## კონტექსტი
კომპანიაში მუშაობს ადგილობრივი პროგრამა **HR Sorter**: ის დასკანერებულ HR დოკუმენტებს (ხელშეკრულება, ბრძანება,
განცხადება, ჯარიმა, შვებულება…) OCR-ით კითხულობს, დოკუმენტიდან იღებს თანამშრომლის **პირად ნომერს**, შემდეგ:
1. MHR-ში პოულობს თანამშრომელს და ადარებს დოკუმენტის მონაცემებს (სახელი, გვარი, კომპანია, თანამდებობა, ხელფასი, ვადები);
2. თუ დოკუმენტი ხელშეკრულებაა — MHR-დან ჩამოტვირთავს **ორიგინალ ხელშეკრულებას** (რომელიც MHR-ში შეიქმნა და
   დაიბეჭდა) და ადარებს დასკანერებულ ხელმოწერილ ასლს, რომ ხელით არაფერი შეცვლილა;
3. თუ ყველაფერი ემთხვევა და ოპერატორი დაადასტურებს — **ატვირთავს დასკანერებულ PDF-ს MHR-ში ამ თანამშრომლის ბარათზე**.

შენი ამოცანაა MHR-ში შექმნა ქვემოთ აღწერილი API (REST, JSON, HTTPS). არსებული API-ის ხელახლა გამოყენება
დასაშვებია, თუ ქცევა ზუსტად ემთხვევა ამ აღწერას.

## ზოგადი წესები
- საბაზო მისამართი: `https://<mhr-host>/api/v1/hr-sorter` (ვერსია URL-ში).
- ავტორიზაცია: `Authorization: Bearer <token>`. ცალკე **ინტეგრაციის ტოკენი** (არა მომხმარებლის), უფლებებით:
  `employees:read`, `documents:read`, `documents:write`. ტოკენი არასდროს გადაეცემა URL-ში.
- ფორმატები: UTF-8 (ქართული ტექსტი), თარიღები `YYYY-MM-DD`, დრო ISO-8601 UTC-ით, თანხები **სტრიქონად** ათწილადით
  (`"2500.00"`) + ცალკე ვალუტა (`"GEL"`), **პირადი ნომერი ყოველთვის სტრიქონია, 11 ციფრი** (საწყისი ნულები არ იკარგება).
- **პირადი ნომერი არ უნდა იყოს URL-ში** (ვებსერვერის ჟურნალებში რომ არ მოხვდეს) — ამიტომ ძებნა POST-ით ხდება.
- შეცდომები ერთიანი ფორმით: `{"error": {"code": "<machine_code>", "message": "<ტექსტი>"}}`.
  კოდები: 400 არასწორი მოთხოვნა, 401 ავტორიზაცია, 403 უფლება, 404 ვერ მოიძებნა, 409 კონფლიქტი,
  413 ფაილი დიდია, 422 ვალიდაცია, 429 ლიმიტი (`Retry-After` ჰედერით), 5xx სერვერი.
- ყოველი ჩაწერის ოპერაცია ჟურნალდება MHR-ის აუდიტში (ვინ — ინტეგრაცია, რა, როდის, `external_id`).

## Endpoint-ები

### 1. თანამშრომლის მოძიება პირადი ნომრით
`POST /employees/lookup`
```json
// მოთხოვნა
{"personal_number": "01001000001"}
// 200
{
  "id": "E001",
  "personal_number": "01001000001",
  "first_name": "ნინო",
  "last_name": "ბერიძე",
  "company": {"id": "acme", "name": "შპს „მაგალითი“", "tax_id": "000000000"},
  "branch": "თბილისი",
  "position": "ბუღალტერი",
  "salary": {"amount": "2500.00", "currency": "GEL"},
  "contract_start": "2020-06-04",
  "contract_end": "2022-06-04",
  "status": "active",            // active | dismissed
  "dismissed_at": null
}
```
- 404 — ამ პირადი ნომრით თანამშრომელი არ არის. 409 — რამდენიმე ჩანაწერი (არ უნდა ხდებოდეს; ინტეგრაცია ავტომატურად არ მიაბამს).
- გათავისუფლებული თანამშრომელიც უნდა მოიძებნოს (`status: "dismissed"`).
- სასურველია (არასავალდებულო): `"employments": [{company, position, salary, start, end}]` — დასაქმების ისტორია,
  ძველი დოკუმენტების სწორად შესადარებლად.

### 2. თანამშრომლის დოკუმენტების სია
`GET /employees/{employee_id}/documents?category=contract`
```json
// 200
{"items": [
  {
    "id": "D-1001",
    "category": "contract",
    "title": "შრომითი ხელშეკრულება",
    "document_number": "0783",
    "document_date": "2020-06-04",
    "created_at": "2020-06-04T09:12:00Z",
    "filename": "contract_0783.pdf",
    "sha256": "…",
    "size": 183244,
    "kind": "generated",          // generated (MHR-მა შექმნა — ორიგინალი) | uploaded (ატვირთული სკანი)
    "external_id": null           // ატვირთულისთვის — HR Sorter-ის document_id
  }
]}
```
- `category` ფილტრი არასავალდებულოა; მის გარეშე — ყველა დოკუმენტი. ახლიდან ძველისკენ დალაგებული.
- `document_number` და `document_date` აუცილებელია ხელშეკრულებისთვის — მათით ვარჩევთ სწორ ორიგინალს, როცა
  თანამშრომელს რამდენიმე ხელშეკრულება აქვს.

### 3. დოკუმენტის ფაილის ჩამოტვირთვა
`GET /documents/{document_id}/file` → `200`, `Content-Type: application/pdf`, ფაილის ბაიტები.
- **მნიშვნელოვანი:** `generated` ხელშეკრულება უნდა იყოს **ციფრული PDF ტექსტური ფენით** (არა სკანი/სურათი) —
  სწორედ ის ტექსტი, რაც დაიბეჭდა. ამაზეა დამოკიდებული შედარების სიზუსტე.

### 4. დასკანერებული დოკუმენტის ატვირთვა თანამშრომელზე
`POST /employees/{employee_id}/documents` — `multipart/form-data`, ჰედერი `Idempotency-Key: <external_id>`
| ველი | სავალდებულო | აღწერა |
|---|---|---|
| `file` | კი | PDF (მაქს. 50 MB) |
| `category` | კი | კატეგორიის კოდი (იხ. endpoint 5) |
| `external_id` | კი | HR Sorter-ის სტაბილური ID (`doc_…`) — იდემპოტენტურობისთვის |
| `sha256` | კი | ფაილის sha256 — MHR ამოწმებს, რომ ფაილი გზაში არ დაზიანდა (არ ემთხვევა → 422) |
| `title` | არა | მაგ. „შრომითი ხელშეკრულება (ხელმოწერილი)“ |
| `document_number`, `document_date` | არა | დოკუმენტიდან ამოკითხული |
| `signed_copy_of` | არა | ორიგინალის `id` (endpoint 2-დან) — „ეს არის ამ ორიგინალის ხელმოწერილი ასლი“ |
| `metadata` | არა | JSON სტრიქონი (ტიპი, წყაროს sha256, შედარების შედეგის მოკლე აღწერა) |
```json
// 201 — შეიქმნა
{"id": "D-2044", "external_id": "doc_5f…", "created_at": "2026-10-28T13:40:00Z"}
// 200 — იგივე external_id უკვე ატვირთულია (ხელახალი მოთხოვნა): აბრუნებს არსებულს, ახალს არ ქმნის
```
- **იდემპოტენტურობა სავალდებულოა:** ერთი და იგივე `external_id`-ით მეორე მოთხოვნამ **არ უნდა შექმნას დუბლიკატი**.
- `category` უცნობია → 422; თანამშრომელი არ არსებობს → 404; არა-PDF → 422.

### 5. დოკუმენტების კატეგორიები
`GET /document-categories` → `{"items": [{"code": "contract", "name": "ხელშეკრულება"}, …]}` —
HR Sorter-ის ტიპები (ხელშეკრულება, დანართი, ჯარიმა, შვებულება, განცხადება, მიღების/გათავისუფლების ბრძანება,
ახსნა-განმარტება) ამ კოდებზე მიიბმება.

### 6. ატვირთვის შემოწმება external_id-ით
`GET /documents/by-external-id/{external_id}` → 200 (ზემოთ აღწერილი დოკუმენტის ობიექტი) ან 404.
- საჭიროა, როცა ატვირთვისას კავშირი გაწყდა და გაურკვეველია, აიტვირთა თუ არა — ორმაგი ატვირთვის თავიდან ასაცილებლად.

### 7. (არასავალდებულო) კომპანიები
`GET /companies` → `{"items": [{"id": "acme", "name": "შპს „მაგალითი“", "tax_id": "000000000", "aliases": []}]}`

## უსაფრთხოება
- მხოლოდ HTTPS; ტოკენი სერვერზე ჰეშირებული; ტოკენის გაუქმება/როტაცია.
- ლიმიტი (მაგ. 120 მოთხოვნა/წთ ტოკენზე), `429` + `Retry-After`.
- პირადი მონაცემები (პირადი ნომერი, სახელი) არ იწერება ტექნიკურ ჟურნალებში.
- წვდომა მხოლოდ შიდა ქსელიდან ან IP-ების თეთრი სიით (თუ შესაძლებელია).

## სატესტო გარემო (აუცილებელია ინტეგრაციის გამოსაცდელად)
- ცალკე **staging** მისამართი და სატესტო ტოკენი.
- სატესტო მონაცემები: მინიმუმ 5 თანამშრომელი —
  1 აქტიური ერთი ხელშეკრულებით; 1 აქტიური **ორი** ხელშეკრულებით (ძველი და ახალი, სხვადასხვა ხელფასით);
  1 გათავისუფლებული; 1 საწყისი ნულით დაწყებული პირადი ნომრით (`00…`); 1 ხელშეკრულების გარეშე.
- თითოეული ხელშეკრულების `generated` PDF ტექსტური ფენით + მათი დაბეჭდილი და დასკანერებული ვერსიები (ტესტისთვის).

## მისაღები შედეგი
1. OpenAPI 3 (Swagger) აღწერა ყველა endpoint-ზე, მაგალითებით.
2. staging გარემო მუშაობს, სატესტო ტოკენი და მონაცემები მზადაა.
3. ტესტები: იდემპოტენტური ატვირთვა (ორი ერთნაირი მოთხოვნა → ერთი დოკუმენტი), sha256-ის შემოწმება,
   პირადი ნომერი საწყისი ნულით, 404/409/422/429 შემთხვევები.
4. ჩასაბარებელი: მისამართი, ტოკენის მიღების წესი, OpenAPI ფაილი, სატესტო მონაცემების სია.
