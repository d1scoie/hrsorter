# გამოყენების ინსტრუქცია (ოპერატორისთვის)

## ყოველდღიური მუშაობა
1. სკანერი PDF-ს დებს `Inbox\Batch` ან `Inbox\Single` საქაღალდეში (იხ. INSTALL_GE.md). თუ სკანერი ყველაფერს ერთ
   საქაღალდეში ყრის (მაგ. პირდაპირ `Z:\`), პარამეტრებში ამ საქაღალდეს მიუთითე რეჯიმით „პროგრამა თავად წყვეტს“ (`auto`):
   1-გვერდიანი PDF ცალკე დოკუმენტად დამუშავდება, მეტგვერდიანი — ნაკრებად (დაიყოფა).
2. პროგრამა ფაილს თავად ხედავს და ელოდება მის ბოლომდე ჩაწერას. სტაბილურობის შემოწმება ნაგულისხმევად 10 წამია
   და მოიცავს ზომის/დროის უცვლელობას, ფაილის თავისუფლად გახსნას და PDF-ის სისწორეს.
3. ორიგინალი ინახება `_Archive`-ში უცვლელად (ჰეშით შემოწმებული). დამუშავების დასრულების შემდეგ (≤30 წმ) ფაილი ინბოქსიდან
   გადადის `Processed\Batch` ან `Processed\Single`-ში, შეცდომით დასრულებული კი `Processed\_Failed\...`-ში. ასე ინბოქსში
   მხოლოდ დაუმუშავებელი რჩება. „თავიდან დამუშავების“ წარმატების შემდეგ ფაილი `_Failed`-იდან `Processed`-ში გადადის.
   ყველაფერი ეს **პარამეტრები → დამუშავებული ფაილები და ადგილი**-ში რეგულირდება:
   - `Processed`-ის ფაილი იშლება N დღის შემდეგ (ნაგულისხმევი 30; ორიგინალი არქივში რჩება). `_Failed` არასდროს იშლება;
   - არქივის ორიგინალი და შედეგის PDF იშლება MHR-ში ატვირთვიდან N დღის შემდეგ (ნაგულისხმევად გამორთულია, 0).
     წყაროს ორიგინალი მხოლოდ მაშინ იშლება, როცა მისი **ყველა** დოკუმენტი ატვირთულია.
     წაშლილ ფაილზე „თავიდან დამუშავება“ აღარ იმუშავებს.
   **მთავარი საქაღალდე ქსელურ დისკზე (მაგ. `Z:`)** შეიძლება იყოს: დოკუმენტები იქ ინახება, პროგრამის ჟურნალი (ბაზა) კი —
   ამ კომპიუტერზე, რადგან ქსელურ დისკზე ბაზა შეიძლება დაზიანდეს. თუ Windows-ში შესვლისას დისკი ჯერ არ არის მიერთებული,
   დამმუშავებელი მას ელოდება. მთავარი საქაღალდის შეცვლისას დამმუშავებელი თავად გადაერთვება; დოკუმენტების სია ახალ
   საქაღალდეში თავიდან იწყება. როცა რამე მუშავდება, საქაღალდის შეცვლა არ შეიძლება.
4. შედეგები:
   - `Sorted\<კომპანია>\<ტიპი>\<წელი>\` — ავტომატურად შენახული (მხოლოდ საცდელი რეჟიმის გამორთვის შემდეგ);
   - `Proposed\...` — საცდელ რეჟიმში შემოთავაზებული შედეგები (იგივე სტრუქტურა);
   - `NeedsReview\<მიზეზი>\` — გადასამოწმებელი;
   - ყოველ PDF-ს გვერდით აქვს ამავე სახელის `.json` ფაილი: საიდან მოვიდა (წყარო და გვერდები), რა ამოიცნო და რამდენად სანდოდ.
5. ვებინტერფეისი: http://127.0.0.1:8765
6. ეკრანის ქვედა მარჯვენა კუთხეში ჩანს „HR“ ხატულა. მწვანე — ყველაფერი რიგზეა, ლურჯი — მუშავდება,
   ყვითელი — გადასამოწმებელი/შეცდომა/შეჩერებული, წითელი — დამმუშავებელი გაჩერებულია. მასზე დაჭერით: რიცხვები,
   „გახსნა“, „გადასამოწმებელი“, „შეჩერება/გაგრძელება“. ახალ გადასამოწმებელზე და შეცდომაზე Windows შეტყობინებას აჩვენებს.
   მენიუში ჩანს **ვერსია** და **„განახლების შემოწმება“**: თუ GitHub-ზე უფრო ახალი ვერსიაა, ის მიმდინარე დამუშავების
   დასრულებისთანავე დაყენდება. პროგრამა რამდენიმე წამით გაითიშება, თავიდან ჩაირთვება და შეგატყობინებს: „განახლდა X → Y“.
   თუ Windows დავალების გაშვებას არ დაუშვებს, ადმინისტრატორის ნებართვას იკითხავს.
   ხელით განახლება საჭირო არ არის: პროგრამა თავად ამოწმებს ყოველ 4 საათში.
   Windows 11 ახალ ხატულებს მალავს `^` ისრის ქვეშ — მუდმივად საჩვენებლად: **Settings → Personalization → Taskbar →
   Other system tray icons → hrsorter-bg** ჩართე.

## ფაილის სახელი
`{თარიღი}_{ტიპი}_{სახელი-გვარი}_{პირადი-ნომერი}_{დოკ.ნომერი}_{მოკლე-ID}.pdf`. თუ რამე უცნობია, ჩაიწერება
`თარიღი-უცნობია`, `სახელი-უცნობია` ან `პნ-უცნობია`. პირადი ნომერი სახელში მხოლოდ სანდოდ ამოცნობისას ხვდება.

## ახალი დოკუმენტის ტიპის დამატება (კოდის გარეშე)
„პარამეტრები" → „დოკუმენტების ტიპები (JSON)"-ში დაამატე ჩანაწერი:
```json
{"id": "reference", "name_ka": "ცნობა", "folder": "ცნობა", "description": "ცნობა სამსახურიდან",
 "positive": [{"pattern": "ცნობა", "weight": 5, "title_only": true}],
 "negative": [], "fields": ["signature_status"], "active": true, "auto_save_enabled": false}
```
`pattern` არის regex ნორმალიზებულ ტექსტზე (პატარა ასოები, ერთი ჰარი, ერთნაირი ბრჭყალები). `title_only` — მხოლოდ
სათაურის ხაზებში. **`auto_save_enabled` ჩართე მხოლოდ რეალურ ნიმუშებზე გამოცდის შემდეგ**; მანამდე ტიპი მხოლოდ შემოთავაზებას ქმნის.
შვებულების განცხადებისა და ბრძანების ცალ-ცალკე შესანახად გამორთე `vacation` და ჩართე `vacation_application` / `vacation_order`.

## საცდელი რეჟიმიდან ავტომატურ შენახვაზე გადასვლა
1. მოამზადე მონიშნული რეალური ნაკრები (იხ. PILOT_REPORT_GE.md) და გაუშვი შეფასება.
2. თუ ტიპისთვის ავტომატურებში ≥99% სწორი ტიპი და ≥99% ზუსტი გვერდებია, ამ ტიპზე ჩართე `auto_save_enabled`.
3. გამორთე „საცდელი რეჟიმი". შედეგები `Sorted`-ში წავა მხოლოდ ჩართული ტიპებისთვის; დანარჩენი ისევ `Proposed`-ში დარჩება.

## MHR: შედარება და ატვირთვა
ჩართვა: პარამეტრები → „MHR ინტეგრაცია“. მისამართები და ავტორიზაცია — „დამატებითში“ (MHR-ის API-ის აღწერის მიხედვით),
გასაღები — „სერვისების გასაღებები“ (`hrsorter/mhr`). დიზაინი: `docs/MHR_DESIGN.md`.

რა ხდება ყოველ სანდოდ დამუშავებულ დოკუმენტზე:
1. პირადი ნომრით MHR-ში ეძებს თანამშრომელს (სახელი, გვარი, კომპანია, თანამდებობა, ხელფასი, ხელშეკრულების ვადები).
2. ადარებს დოკუმენტიდან ამოკითხულს. სახელი/გვარი შედარდება ბრუნვისა და OCR-ის წვრილი შეცდომების გათვალისწინებით.
3. **ხელშეკრულებისას** MHR-იდან ჩამოტვირთავს ორიგინალს და ადარებს ტექსტს: შეცვლილი ციფრები, დამატებული ან ამოღებული
   წინადადება, ხელით მიწერილი — ცვლილებაა; OCR-ის წვრილი შეცდომები — არა (ჩანს ცალკე, „ხმაურად“).
   თუ ხელშეკრულება ორიგინალს ემთხვევა, MHR-ის **ამჟამინდელი** ხელფასის/თანამდებობის სხვაობა მხოლოდ შენიშვნაა.
   თუ MHR-ში ამ თანამშრომლის ხელშეკრულება ჯერ არ არის, სკანი **თანამდებობის შაბლონს** შედარდება (MHR ირჩევს
   თანამდებობითა და ხელშეკრულების ტიპით): შაბლონის ცვლადების (სახელი, პ/ნ, თარიღები, ხელფასი, რეკვიზიტები) ადგილას
   რაც წერია, სხვაობა არ არის; პუნქტების ნუმერაცია, ტექსტში ჩაწერილი ბეჭდის ასოები და რეკვიზიტების ცხრილის წაკითხვის
   რიგი — ხმაურია. ნამდვილი ცვლილება (სხვა ციფრი, სხვა სიტყვა, ჩამატებული წინადადება) ჩანს.
   **ხელმოწერა მოწმდება ყველა გვერდზე, ორივე მხარისთვის ცალ-ცალკე** („დამსაქმებელი“ და „დასაქმებული“/„სტაჟიორი“
   წარწერის ქვეშ ხელმოწერა ან ბეჭედი, ლურჯი კალმითაც): რომელიმეს აკლია → „გვერდი N: ხელმოწერა აკლია: …“ და
   დოკუმენტი „ვერ გაიარა“. გვერდი, რომელზეც ხელმოწერის ხაზი საერთოდ არ იბეჭდება (ტექსტი კარგად იკითხება, წარწერა
   არ არის), მხოლოდ შენიშვნას იძლევა. გამორთვა: პარამეტრები → MHR → „ხელშეკრულებაზე ხელმოწერა ყველა გვერდზე“.
   **პაკეტი:** თუ MHR-ში ხელშეკრულებასთან ერთად თანამდებობრივი ინსტრუქცია და დანართებიც გენერირებულია და ყველა
   ერთად დაასკანერე, პროგრამა თითოეულ გვერდს თავის დოკუმენტს შეადარებს (დეტალებში „დანართი: გვ. …“). დანართის
   სხვაობა სიაში ჩანს, მაგრამ ატვირთვას არ აჩერებს — ბლოკავს მხოლოდ ხელშეკრულების სხვაობა და ხელმოწერის ნაკლი.
4. შედეგი ჩანს გვერდზე **MHR**: „მზადაა“ (ვალიდაცია გავიდა), „ვერ გაიარა“ (ზუსტად რა განსხვავდება: ველების ცხრილი და
   ორიგინალ/დასკანერებული ტექსტის ფრაგმენტები), „მიმდინარე“, „ატვირთულია“, „სხვა“.
5. **ატვირთვა მხოლოდ შენი დადასტურებით** („ატვირთვა“ ან „ყველას ატვირთვა“ — ეს ღილაკი მთავარ გვერდზეც ჩანს, როცა რამე
   მზადაა: ერთი დაჭერით ყველა შემოწმებული ხელშეკრულება შესაბამის თანამშრომელს აეტვირთება). ატვირთვას ფონური პროცესი
   აკეთებს ~1 წუთში.
   ერთი დოკუმენტი ორჯერ არასდროს იტვირთება; თუ ატვირთვის შედეგი გაურკვეველია (კავშირი გაწყდა), ჩანაწერი
   გადადის „საჭიროებს შემოწმებას“ — შეამოწმე MHR-ში და მხოლოდ შემდეგ სცადე ხელახლა.
6. **„ატვირთვა მაინც“** — „ვერ გაიარა“ დოკუმენტზე, თუ სხვაობა ცრუა (მაგ. ბეჭედი ან ხელმოწერა ცვლილებად ჩაითვალა):
   ჯერ ნახე სხვაობები, მონიშნე „ქვემოთ მოცემული სხვაობები ვნახე — დოკუმენტი სწორია“ და დააჭირე. ეს შენს
   გადაწყვეტილებად იწერება ჟურნალში. მხოლოდ მაშინ ჩანს, როცა თანამშრომელი MHR-ში მოიძებნა.
7. დოკუმენტის გვერდზე (MHR ჩართულისას) ჩანს სტრიქონი **MHR**: მოიძებნა თუ არა თანამშრომელი და სად არის პროცესში;
   ღილაკი „MHR შედარება“ ხსნის დეტალურ შედარებას.
8. **ხელით ატვირთვა** — როცა ავტომატური შედარება ვერ გადის, დოკუმენტი „გადასამოწმებელში“ დარჩა ან ტიპი უცნობია,
   და ატვირთვა მაინც გჭირდება. ორი გზა:
   - **თავად დოკუმენტიდან (მთავარი გზა):** დოკუმენტის გვერდზე ან MHR-ის დეტალებში ბარათი „ხელით ატვირთვა“ → ღილაკი
     „ხელით ატვირთვა MHR-ზე“. პირადი ნომერი დოკუმენტიდან უკვე წაკითხულია — პროგრამა MHR-ში იპოვის თანამშრომელს და
     მაშინვე ატვირთავს; შედეგი იქვე ჩანს („ატვირთულია MHR-ზე — სახელი გვარი“). უცნობი ტიპის დოკუმენტს ჯერ ტიპს აურჩევ.
     „ვერ გაიარა“ დოკუმენტზე, სადაც თანამშრომელი უკვე მოძებნილია, ამავე ადგილას „ატვირთვა მაინც“ ღილაკია (პ. 6).
   - **გვერდი „ხელით ატვირთვა“** (მენიუში, MHR ჩართულისას) — როცა პირადი ნომერი სკანიდან ვერ წაიკითხა:
   - ჩაწერე თანამშრომლის **პირადი ნომერი, სახელი და გვარი** ისე, როგორც MHR-შია → „მოძებნა MHR-ში“.
   - პროგრამა პირადი ნომრით MHR-ში იპოვის თანამშრომელს და შეადარებს სახელ-გვარს. თუ არ ემთხვევა, აჩვენებს, ვინ წერია
     MHR-ში ამ ნომერზე, და დოკუმენტებს **არ** აჩვენებს — ასე სხვის ბარათზე ვერაფერს ატვირთავ.
   - დამთხვევისას ჩანს ამ პირადი ნომრის **აუტვირთავი დოკუმენტები** („ატვირთვა“ თითოეულზე ან „ყველას ატვირთვა“) და ცალკე —
     **სავარაუდო დოკუმენტები სახელით**: პირადი ნომერი სკანიდან ვერ წაიკითხა ან სხვა გამოვიდა, მაგრამ სახელ-გვარი ემთხვევა.
     ამათზე ჯერ PDF გახსენი და დარწმუნდი. უცნობი ტიპის დოკუმენტს ჯერ ტიპი აურჩიე (MHR-ის კატეგორია ტიპიდან დგება).
   - ატვირთვა **მაშინვე** ხდება, ავტომატური შედარების გარეშე; შედეგი გვერდის თავში ჩანს. თუ MHR მიუწვდომელია, ჩანაწერი
     „დადასტურებული“ რჩება და ფონური პროცესი თავად სცდის მოგვიანებით. ჟურნალში ეს შენს გადაწყვეტილებად იწერება
     („approved manually“), MHR-ის დეტალებში — „ხელით ატვირთვა — ავტომატური შედარება გამოტოვებულია“.
   - უკვე ატვირთული ან პროცესში მყოფი დოკუმენტი ხელით მეორედ არ იტვირთება (ჩანს ჩამოსაშლელ სიაში „უკვე ატვირთული ან პროცესში“).

## რამდენად კარგად კითხულობს ტექსტს (OCR ტესტი)
**თვალით:** ინტერფეისში გახსენი დოკუმენტი → „ამოკითხული ტექსტი“. ყოველი გვერდის სკანი და პროგრამის მიერ
წაკითხული ტექსტი გვერდიგვერდ ჩანს, ხარისხის ქულით (მწვანე ≥ 0.8 კარგი, წითელი ცუდი).

**ზუსტად (CER/WER):**
1. აირჩიე 5–10 გვერდი სხვადასხვა ხარისხით და გაუშვი:
   `hrsorter.exe ocr-test "C:\scans\file.pdf" --pages 1,5,9 --out C:\ocr_test`
   (`C:\ocr_test`-ში შეიქმნება `page_001.png`, `page_001.txt` … და `report.html`).
2. შექმენი საქაღალდე `C:\ocr_test\truth`, დააკოპირე იქ `page_*.txt` ფაილები და **Notepad-ით გაასწორე**
   ყოველი შეცდომა სკანის მიხედვით (ეს არის „სწორი ტექსტი“). ხაზების დაყოფას მნიშვნელობა არ აქვს.
3. გაუშვი ისევ, `--truth`-ით: `hrsorter.exe ocr-test "C:\scans\file.pdf" --pages 1,5,9 --out C:\ocr_test --truth C:\ocr_test\truth`.
4. `report.html`-ში ჩანს **CER** (ასოების შეცდომის %), **WER** (სიტყვების შეცდომის %), პირადი ნომრების სწორად წაკითხვა,
   და ფერადად — სად შეცდა (<del>წითელი</del> = OCR-ის ვერსია, მწვანე = სწორი).

შეფასება: CER < 2% ძალიან კარგი · 2–5% კარგი · 5–10% საშუალო · > 10% ცუდი. ტიპის ამოცნობისთვის 5%-მდე CER
ჩვეულებრივ საკმარისია; პირადი ნომრისთვის მნიშვნელოვანია, რომ ციფრები ზუსტად იკითხებოდეს.

## ბრძანებები
```powershell
.venv\Scripts\python.exe -m hrsorter.cli status          # მდგომარეობა
.venv\Scripts\python.exe -m hrsorter.cli pause           # შეჩერება (მიმდინარე ფაილი დასრულდება)
.venv\Scripts\python.exe -m hrsorter.cli resume
.venv\Scripts\python.exe -m hrsorter.cli reprocess <job_id>
.venv\Scripts\python.exe -m hrsorter.cli run-once        # ერთჯერადი დამუშავება (worker-ის გარეშე)
.venv\Scripts\python.exe -m hrsorter.cli --config D:\other\config.json status
```
ხელახალი დამუშავებისას ძველი შედეგები გადადის `_Superseded`-ში (არ იშლება). ერთ დოკუმენტს ორი აქტიური შედეგი არ რჩება.
